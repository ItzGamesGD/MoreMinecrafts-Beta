## Validation limits

`KnowledgeConditionSemanticsTest` covers success versus failure predicates, item consumption, blast furnace craft-plus-output conjunction, bow/crossbow key distinction, threshold boundaries, persistent attachment codec round-trip, and distinct food-key deduplication. These are focused unit checks, not proof that Fabric mixins execute in a live server.

No Stage 2-B action-level GameTest has yet demonstrated these hooks. In particular, K12 crafting/output attribution, K18/K19 placement callbacks, K22/K23 world transitions, K25 species attribution, K30 cooking statistics, and K34–K38 real damage-source attribution remain **IMPLEMENTED_NOT_RUNTIME_VERIFIED** pending CI/runtime evidence.

## Stage 2-A integration and regression audit (2026-10-12)

Verified remote sources before integration: PR #79 `204f706cb2ffd1bf60fa950f201a33446b55850f`, PR #80 `cba72162ecd5c80f1101d9a2024d6c3647acc1a9`, common ancestor `04fd5780658f847f74be6beda76754e08a0b5520`. The authority index, Research/Knowledge tier design, approved node-tree spec, and node-tree manifest have identical Git blob IDs at all three commits. The PR bodies and status documents were treated as implementation claims, not authority changes. PR #79 remains untouched.

The integration retains Stage 2-B's observers and merges Stage 2-A's later stabilization commits. In `KnowledgeRuntime.recordCondition`, Stage 2-A's `KnowledgeConditionProgress.advance` now caps the shared counter at the maximum target for every matching catalog entry; each entry is then evaluated independently. This preserves K31/K32, K60/K62, and K63/K69 progress without disturbing Stage 2-B's K5/K8 pauses, K14 quantity behavior, placement/feeding/food observers, or projectile kill attribution. `KnowledgeEventCollectors` retains both stages' methods. The furnace output hook invokes both K12's blast-furnace collector and K11's provenance collector. The projectile launch hook retains K40 special-ammunition observation and K34/K35 origin capture. The mixin list retains all Stage 2-A and Stage 2-B registrations, with no duplicate names. Furnace and brewing version-1 provenance codecs and save/load hooks are present in the combined tree. Unlock announcements and silent join reconciliation remain in `KnowledgeRuntime`.

After the K19 correction below, local `./gradlew clean test build compileGametestJava runGameTest` completed with 213 JUnit tests and all 34 required GameTests passing. The new GameTest exercises one successful redstone-dust placement; the other eleven Stage 2-A collector actions, the other Stage 2-B acquisition actions, furnace/brewing output save-reload scenarios, and notification delivery are not exercised. One preceding full run passed unit/build tasks and the new K19 test but failed the unrelated custom-mob stat-idempotence GameTest, which had passed in the earlier 33-test run and passed in the final 34-test run. Compilation and startup must not be reported as action-level verification for other conditions.

The final-tree dedicated server smoke reached registry/common initialization and `Done` readiness. A local `runClient` attempt timed out after 65 seconds during Gradle's `downloadAssets` task, before the client process started. Client startup requires separate CI evidence; this local attempt does not verify rendering or UI behavior.

The audit found a K19 double count in Stage 2-B's preexisting redstone path: Minecraft 26.3 registers `Items.REDSTONE` as a `BlockItem`, so one successful placement reached both `KnowledgeBlockPlacementMixin` and `KnowledgeItemUseMixin`. A new action-level GameTest placed one dust item and failed on the expected single increment before the fix. `KnowledgeBlockPlacementMixin` now leaves dust to the existing `KnowledgeItemUseMixin` observer; other eligible block placements continue through the BlockItem observer. This is a narrowly scoped correction to retain K19's intended one-event-per-placement behavior. Other K19 placement scenarios remain unverified.

Crossbow firework attribution remains temporary: launch records the player's UUID against the live `FireworkRocketEntity`; a hostile death is credited only when the direct damage entity is that same projectile and the player is still online. Vanilla's firework damage source uses the rocket as direct entity, but the weak map has no reload codec. A launch-to-kill test, explosion splash attribution test, disconnect test, and projectile save/reload test are still needed. Bow and crossbow arrows instead use the arrow's persisted weapon and owner; tridents use the direct thrown trident's stored weapon and owner. K40 special-ammunition launch observation is separate from kill credit.

Decisions still needed from the user: for K5, which large trees qualify and what proves collected logs came from one; for K8, the eligible eight-or-more survival-reachable rock roster; for K14, the complete set of craftable tools counted toward the already approved quantity of five. No distinct-tool requirement has been inferred.
