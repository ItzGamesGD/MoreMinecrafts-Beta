# ST-01 P10 — O-1 대체 개방 시간 후보 (산출물 5)

상태: **측정 결과와 후보 제시. 운영 대기 시간은 확정하지 않았다**(운영에는 여전히 기본값이 없고 `EntranceConfig`가 설치되지 않으면 입구 런타임은 비활성이다). 아래 틱은 모두 "유효 승리 직후부터 센 서버 틱"(20틱 = 1초)이다. 원자료: `data/suite/route_trials_base.csv`, `data/suite/flow_runs.csv`, `data/load/*.csv`, 계산 `tools/st01-p10/o1_candidates.py`.

## 1. 정상 도착 시간의 분포 (실제 왕실 기하)

### 1.1 골렘 이동만 (플레이어 대기 없음, 540회 = 9 출발점 × 동/서 × 30)
- 전체: 최소 128, 중앙값 209.5, p90 349, p95 350, p99 350, 최대 350.
- **P9 기본 생성 칸(BOSS_S)**: 146–155 (중앙 153). 시작 지연은 일정하다: 첫 경로가 생기기까지 **20–21틱**(540/540).
- 가장 먼 후보: 홀 입구 안 296, 문 밖 통로 330, 북서 모서리 350.

### 1.2 전체 파이프라인 + 동행하는 참가자 (동·서 각 32회 = 64회, `RoyalTombFlowGameTests`)
참가자는 **시뮬레이션**(시험이 위치를 직접 옮기는 모의 서버 플레이어, 충돌·클라이언트 없음)이다. 매 회차 시작 거리 2–16칸, 상자를 터는 시간(루팅 지연) {0, 60, 120, 240}틱, 걸음 속도 {0.12, 0.20, 0.27}칸/틱을 시드 고정으로 뽑았다. 서쪽은 시작 거리의 방향도 거울이다.

- 64회 전부 `ENTRANCE_OPEN`(정상 도착)이며 대체 개방 0회: 최소 149, 중앙 208.5, p90 385, p95 401, 최대 404.
- 리더가 시작 후 10칸보다 멀어지면 골렘이 **기다린다**(P9 설계). 그래서 도착 시간 ≈ 이동 시간 + 리더가 따라붙기까지의 시간이다. 루팅 지연이 240틱(12초)이면 가까이 있어도 골렘이 먼저 출발해 10칸을 벗어나므로 311–404틱이 걸렸다.
- 동·서가 같은 입력에서 같은 틱으로 열린다(동 중앙 208.5 = 서 중앙 208.5).

### 1.3 정상 도착이 없는 경우 (모두 대체 개방으로 끝남, 600틱 시험값)
| 상황 | 시행 | 결과 |
| --- | --- | --- |
| 유일한 참가자가 14–20칸 밖에서 움직이지 않음 | 4 | 4/4 `FALLBACK_OPEN` @ 601 (골렘은 기다림) |
| 안내 중 청크 언로드 | 3 | 3/3 `FALLBACK_OPEN` @ 601, 재로드 시 덮개 12칸만 적용(복셀 불일치 12) |
| 라이브 상태 소실(`forgetLiveState`) | 4 | 4/4 `FALLBACK_OPEN` @ 601 — **골렘은 154–155틱에 도착했으나 입구 기록이 감지하지 못함**(산출물 4) |
| 경로 차단(음성 대조: 홀을 가로지르는 벽) | 1 | `FALLBACK_OPEN` @ 601, 도착 판정 없음 |

## 2. 대체 개방과 정상 도착의 경합 (실제 기하, 시험 타이머 600틱)
골렘 속도 속성을 조절해 도착 시점을 600틱 부근에 맞췄다(보정: 산출물 7 §3). 12회.

| 골렘 속도 속성 | 결과 | 개방 틱 | 정지 칸까지 거리 / 덮개 간격 |
| --- | --- | --- | --- |
| 0.1200 | 정상 도착 | 509 | 1.46 / 2.61 |
| 0.1150 | 정상 도착 | 552 | 1.47 / 2.62 |
| 0.1120 · 0.1110 | 정상 도착 | 573 · 574 | 1.46 / 2.62 |
| 0.1105 · 0.1095 · 0.1090 · 0.1100 | 정상 도착 | 594 · 595 · 595 · 599 | 1.45–1.46 / 2.60–2.62 |
| 0.1080 | **대체 개방** | 601 | 1.95 / 3.11 (아직 도착 전) |
| 0.1060 · 0.1040 · 0.1000 | **대체 개방** | 601 | 2.51–3.07 |

- 8/12는 599틱 이전에 정상 도착, 4/12는 601틱에 대체 개방. **어느 쪽이든 덮개는 정확히 한 번 열리고(복셀 불일치 12 = 덮개 12칸), 상태가 되돌아가지 않았으며, 두 번째 개방이 없다.**
- 같은 단계에서 타이머가 0이 되고 골렘도 반경에 들어와 있으면 `EntranceCore.step()`의 순서(`tick()` → `pumpSpawn()` → `pollArrival()`) 때문에 대체 개방이 먼저 상태를 정하고 `pollArrival()`은 `GOLEM_GUIDING`에서만 상태를 바꾸므로 **동시 발생 시 FALLBACK_OPEN이 이긴다**(코드 판독 + P7 기준 시퀀스 단위 테스트; 이번 12회에서 정확한 동시 틱은 나오지 않았다).

## 3. 서버 부하와 도착 틱
서버 틱 길이를 억지로 늘린 부하(틱마다 바쁜 대기)에서도 틱 단위 도착 시간이 변하지 않았다.

| 부하 | 평균 서버 틱 | BOSS_S 도착(중앙·최대, n=12–24) | DOOR_IN 도착(n=6–12) |
| --- | --- | --- | --- |
| 없음(참고) | 2–10 ms | 153 (155) | 296 (296) |
| 60 ms 추가 | 64 ms | 154 (155) | 296 (296) |
| 150 ms 추가 | 154 ms | 154 (155) | 295.5 (296) |
| 250 ms 추가 | 254 ms | 154 (155) | 295.5 (296) |

→ 서버가 5배 느려져도 **틱 단위** 도착 시간은 같다. 대체 타이머가 틱 단위이므로(`EntranceCore.remaining`은 서버 틱마다 감소) 서버 부하는 "골렘이 더 늦게 도착"하게 만들지 않는다(실시간으로는 당연히 길어진다).

## 5. 권장(제안, 승인 아님)
- 측정 기준으로 **T-300은 부적합**하다(정상 흐름의 25%를 가로채고 먼 생성 칸에서는 구조적으로 불가능).
- **T-450 이상이 필요**하며, 표본의 최대(404틱)에 안전 여유를 두려면 **T-600(30초)**을 출발점으로 삼는 것이 데이터와 가장 잘 맞는다. 더 길게(T-900/1200) 잡을 이유는 "플레이어가 상자를 털며 10칸 이상 떨어져 머무르는 시간"의 분포가 필요한데 **이번에 측정하지 못했다**(실제 플레이 없음). 그 분포가 있으면 `T ≥ 이동 시간(≈ 150–350) + P95 루팅 지연 + 여유`로 정할 수 있다.
- 서버 부하는 이 값에 영향을 주지 않으므로(§3) "느린 서버 때문에 늘리는" 보정은 필요 없다.
- 최종 O-1 값은 사용자가 정한다.

## 6. 한계
- 참가자 거동(시작 거리·루팅 지연·걸음 속도)의 범위는 시험자가 정한 것이며 실제 플레이 분포가 아니다. 모의 플레이어는 충돌 없이 직선으로 따라오고, 입력/클라이언트가 없다.
- 위 표의 비율은 "표본 안에서"의 값이다. 표본이 독립이 아니고(결정적 시뮬레이션) 분포 일반화는 할 수 없다.
