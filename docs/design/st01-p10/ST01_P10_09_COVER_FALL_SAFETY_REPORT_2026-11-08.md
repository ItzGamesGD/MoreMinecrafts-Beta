# ST-01 P10 — 덮개 개방과 낙하 안전성 보고 (산출물 9)

상태: **실제 서버에서 측정 완료, 단 점유자는 모두 대리/모의이다.** 덮개 개방은 운영 코드의 `McPorts.openCover()`(12칸을 `AIR`로, `UPDATE_ALL`)를 그대로 호출했다. 실제 플레이어 접속이 없어 **"실제 플레이어가 덮개 위에 서 있을 때"는 검증하지 않았다**(UNVERIFIED). 대리 점유자: 갑옷 거치대(낙하량이 결정적), AI 주민(실제 낙하 피해), 금 안내 골렘, **모의 서버 플레이어**(`ctx.makeMockServerPlayerInLevel()` + 매 틱 `doTick()`으로 물리 구동; 클라이언트·입력 없음). 구조물 기하는 변경하지 않았다. 원자료: `data/suite/cover_safety.csv`, `data/suite/hatch_walk.csv`, `data/extra/route_trials_open.csv`.

## 1. 덮개 아래의 실제 지형 (실제 기하)
덮개 12칸(동 X −9..−6, 서 X 6..9, Z 33..35)은 홀 바닥 위층(Y=−23)이고, 그 아래는 P4-B의 측면 계단이다. 열(앵커 기준 dx)별 낙하 깊이:

| dx (동쪽) | 12 | 13 | 14 | 15 |
| --- | --- | --- | --- | --- |
| 갑옷 거치대 낙하량 | 1.0 | 2.0 | 3.0 | **4.0** |
| (열마다 Z 0..2 세 칸) | 1.0 ×3 | 2.0 ×3 | 3.0 ×3 | 4.0 ×3 |

서쪽은 부호 반전으로 동일(−12…−15에서 1/2/3/4). **최대 4블록 낙하**가 확인됐다(P6 CO5 정적 계산 4와 일치).

## 2. 덮개 개방 시험 결과 (동/서, 12칸 위에 동시 점유 20개체)
각 쪽에서 12칸 모두에 갑옷 거치대 1개, 4열(dz=0)에 AI 주민 4명, 모의 플레이어 2명(dx 13 열과 가장 깊은 dx 15 열), 금 안내 골렘 1(덮개 위) + 1(정지 칸)을 동시에 올려 두고 개방했다(12 + 4 + 2 + 2 = 20개체).

| 점유자 | 낙하량(블록) | 결과 |
| --- | --- | --- |
| 갑옷 거치대 12개 | 1.0/2.0/3.0/4.0 (열 깊이대로) | 12/12 생존, 매몰 0 |
| 모의 플레이어(dx 13) | 2.0 | 피해 없음(20→20; 낙하 < 3은 피해 없음), 생존 |
| 모의 플레이어(가장 깊은 dx 15 열) | **4.0** | 생존, 매몰 없음. **피해 0은 피해 측정으로 해석하면 안 됨**(아래 §3) |
| 덮개 위 금 안내 골렘 | 1.0 | 생존(일반 피해 무시), 매몰 없음 |
| 정지 칸의 금 안내 골렘 | 0.0 | 위치 불변 |
| AI 주민 4명(열마다 1명) | 이동하며 1.0–2.6 (제자리 개체 2.0) | 4명 중 1명씩(동·서 각 dx 15 열 개체) 20→19 — AI라 실행마다 변동 |

- **매몰 0, 사망 0, 개방 후 12칸을 제외한 월드 변화 0**(개방 후 복셀 불일치가 정확히 12칸).
- 동시 점유 20개체가 한꺼번에 낙하해도 서로를 막거나 묻지 않았다.

## 3. 4블록 낙하와 피해
- 바닐라 규칙: 낙하 4블록 → 피해 `ceil(4 − 3) = 1`(하트 반 칸), 3블록 이하는 피해 없음.
- 측정: 갑옷 거치대(낙하량 4.0)는 피해 개념이 없다. **AI 주민은 가장 깊은 열(dx 15)에서 동·서 모두 20→19(피해 1)** 를 받아 바닐라 규칙과 일치한다(P9 측정도 4.0 낙하에서 20→19). 다른 열의 주민(낙하 1–2.6)은 피해가 없었다.
- **모의 플레이어는 4.0 낙하에서도 피해 0**이었다. 서버 쪽 플레이어 낙하 피해는 클라이언트가 보고하는 지면 상태에 의존하는데, 모의 플레이어는 클라이언트 패킷이 없어 이 경로를 타지 않는다. 따라서 **"플레이어가 4블록 낙하 시 정확히 얼마의 피해를 받는가"는 이번 시험으로 검증되지 않았다(UNVERIFIED)**. 생물 엔티티(주민)의 피해만 근거로 삼는다.

## 4. 개방 후 이동 가능성
| 시험 | 결과 |
| --- | --- |
| 정지 칸의 scale 0.5 골렘 → `HATCH`(계단 입구 위) | 동 16틱, 서 16–17틱 도달 |
| scale 0.5 골렘 → `VAULT_ENTRY`(지하 금고 입구) | 동·서 모두 **214틱** 도달 |
| scale 0.75 / 1.0 골렘 → `HATCH` | 도달(16–17틱) |
| scale 0.75 / 1.0 골렘 → `VAULT_ENTRY` | **1200틱 안에 미도달**(좁은 복도/계단 높이 제약으로 추정, 경로 로그는 없음) |
| 개방 후 덮개 곁을 걷는 골렘 54회(동/서, 동쪽 통로 접근 포함) | 구멍으로 **낙하 0** (몸체-덮개 간격 최소 0.14) |

플레이어 크기(0.6×1.8) 개체의 개방 후 통행은 P6 BF1의 정적 BFS(1칸 폭·높이 2)에서 검증됐고, 이번에는 대신 골렘(0.7×1.35 이상)으로 같은 구간을 걸어 보았다. **플레이어 크기의 AI 개체는 보내 보지 않았다.**

## 5. 재시작 후 OPEN 유지
실제 서버 프로세스 3개(write → reload → verify)를 두 모드로 실행했다(`tools/st01-p10/run_restart.sh`, 실제 왕실 묘실 위).

| 모드 | write | reload | verify |
| --- | --- | --- | --- |
| `open` (정상 도착으로 OPEN 후 저장) | `ENTRANCE_OPEN`, 복셀 불일치 12 | `ENTRANCE_OPEN` 유지, 덮개 열림 유지, 골렘 없음 | 두 번째 재시작 후에도 OPEN, 승리 기록·상자 봉인 해제 유지, 재진행 없음 |
| `guiding` (안내 중 저장, 골렘 소실) | `GOLEM_GUIDING`, 남은 600틱 | `GOLEM_GUIDING`/`FALLBACK_OPEN`로 복원, 대체 타이머로 개방 | OPEN 유지 |

## 6. 판정과 한계
- **PASS(대리/모의 점유자):** 덮개 12칸 개방은 열 깊이대로(최대 4블록) 낙하시키고 매몰시키지 않으며, 동시 다수 점유에서도 문제가 없다. OPEN은 재시작 후 유지된다.
- **UNVERIFIED:** 실제 플레이어(서버 연결·낙하 피해 동기화·클라이언트), 여러 실제 플레이어가 동시에 덮개 위에 서 있는 경우, 개방 연출(O-12는 미구현: 블록 즉시 제거), 낙하 후 플레이어가 탈출하는 실제 조작.
- P6 CO6의 "점유 중 복원" 위험은 운영이 덮개를 되돌리지 않으므로(P9: 자동 폐쇄 없음) 발생하지 않는다.
- 미결정(O-5 낙하 가장자리 처리)은 변경하지 않았다.
