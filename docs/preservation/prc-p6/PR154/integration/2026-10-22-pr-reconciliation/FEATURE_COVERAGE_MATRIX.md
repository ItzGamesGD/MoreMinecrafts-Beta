### Confirmed cause versus hypotheses

At main, `client/ProgressionSelectionScreen.java:19–24` sets XP `enabled=false`, and `:64–75` returns for disabled targets and has no XP dispatch. `ProgressionBrowseScreen:22` has only KNOWLEDGE/RESEARCH. The downloaded integration branch differs from main in exactly one added path: `docs/design/xp-quest/INTEGRATION_CHECKPOINT_2026-10-20.md` (48 lines). Its two commits record an audit/stop, not UI code. Resource loading, client/server sync or an unregistered menu are not needed to explain that XP failure. These progression Screens are constructed directly with `minecraft.gui.setScreen`; there is no missing Screen registry step to perform blindly.

Knowledge has the opposite source evidence: `ProgressionAdvancementKeyMixin:13–17` opens the selector and is registered in main's mixin JSON; the enabled Knowledge switch opens `ProgressionDisciplineSelectionScreen`, whose `:185–204` dispatches to the selected Knowledge canvas. Main's node layout independently parses as 70 knowledge nodes: resources10, production9, living11, combat10, ecology12, world10, alchemy8. No missing Knowledge catalog or deliberately disabled route was found. Main's selector lacks explicit keyboard navigation; that is a separate confirmed limitation repaired by #126. Installed-JAR mismatch, different loaded branch/mod, mixin/event failure, GUI-scale hitbox error, resource error or runtime exception remain **hypotheses** for mouse failure until the exact artifact and event/transition evidence are captured. No synchronization or resource failure was confirmed as its cause.
